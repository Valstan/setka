Найдено побочно при разборе молчания ИИ-фильтра. В `logs/celery-worker.log` — **2602 строки
с полным community-токеном** `COMM_137760500` (тот самый токен Радара, что восстанавливали
25.07), в виде `access_token=vk1.a.…` внутри URL из INFO-лога `httpx`.

**Почему маскирование не сработало — промахнулись ОБА слоя сразу.** `httpx` логирует
`logger.info("HTTP Request: %s %s", request.method, request.url)`, где `request.url` — **объект**
`httpx.URL`, а не строка. Слой «по форме» его не видел: `_redact_arg` возвращал не-строки как
есть, а склейка в `record.getMessage()` происходит ПОСЛЕ фабрики — то есть после
единственного места, где маскирование вообще случается. Слой «по значению» тоже промахнулся:
community-токены живут в БД (единый источник, решение 12.07), а не в окружении, и их значений
фабрика не знает. Оба слоя были построены «ни один не заменяет другой» — оказалось, что
существует класс случаев, где отказывают оба.

Это третий заход одного класса (G235 → G239 → этот): секрет попадает в лог не тем путём,
на который написана защита. Обобщённая формулировка для мозга: **тест на маскирование обязан
воспроизводить не только текст из лога, но и ТИП аргумента, которым этот текст туда попадает.**

**Сделано (этот PR):** `_redact_arg` маскирует любой аргумент, чья строковая форма несёт
секрет (числа остаются числами — `%d` не ломается). Три регресс-теста; проверено, что на
старом коде они падают. Заодно починены три старых теста, которые в полном прогоне шли
по ПУСТОМУ выводу (`caplog.at_level(INFO)` без имени логгера не поднимает `httpx` с WARNING)
— зелёные от отсутствия данных, охраняли ничего.

**Права логов в порядке** (640 файл / 750 каталог) — в отличие от инцидента 12.08 (644/775),
то есть утечка ограничена боксом. Других форм в логах нет: Telegram-токенов в пути — 0, `Bearer` — 0.
