- ⚠️ **Снятый вывод — и как я к нему пришёл.** Днём 25.08 я записал сюда «в схеме D-035 круг:
  комната недостижима с этой машины, а тоннель к ней требует того самого ключа». **Неверно.**
  Недостижим был **HTTP-клиент**, а не комната: на Windows `curl` собран со schannel, сервер
  запрашивает TLS-ренеговорот, и schannel уходит в цикл до таймаута. По слоям: сырой TCP на
  443 — OK, `openssl s_client` — OK (TLS 1.3, сертификат валиден), Python `urllib` напрямую
  **без тоннеля** — `401`, то есть достижимо. Схема валидна, тоннель был не нужен.
  **Почему три перепроверки не спасли:** прокси / обход прокси / вне песочницы — три разных
  **условия**, но один и тот же **прибор**; слепота жила в curl, общем для всех трёх.
  Повторить проверку сильнее — не то же самое, что проверить иначе.
- 🛠 **Практический остаток:** vault-клиент на Windows не должен ходить через системный `curl`
  — Python (OpenSSL) работает, curl зависает.
- 🛠 **Грабли (полностью — в письме `2026-08-25-d035-pilot-passed-six-gotchas-*`):**
  CRLF ломает ключ **не в JSON, а в трубе** (текстовый `stdout` Python на Windows: 399 → 406
  байт, `ssh-add` падает как `error in libcrypto`; лечится `sys.stdout.buffer`);
  `IdentitiesOnly=yes` отсекает **и агентские** ключи, изолировать диск надо
  `-o IdentityFile=/dev/null`; **подмена `HOME` на Windows ssh не изолирует** (читается
  `%USERPROFILE%`) — первая симуляция прошла зелёной, используя настоящий ключ с диска;
  троттлинг sshd после серии отказов неотличим от поломки (нужны паузы ~40 с).
- 🟡 **Побочное из осмотра:** `~/.ssh/id_rsa` — на самом деле ED25519 (имя историческое);
  один и тот же ключ в `authorized_keys` прода **дважды** (отзыв «по имени» сработает
  наполовину); алиасы `setka`, `myserver`, `sarafan` ведут на один бокс одним ключом —
  переименование #512 оставило два прежних.
