Решение владельца: внутри экосистемы стандартные подключения делаются **без человека в цикле**.
Оба канала SETKA — клиент ЕСА и ключ VK-шлюза — выдаются **одной процедурой и одним ключом**
(`X-Ecosystem-Key`), ядро общее у HTTP и CLI (`modules/ecosystem/provisioning.py`), поэтому
разъехаться правилами им нечем.

- ✅ **Построено:** `POST /api/ecosystem/oidc-clients` (узкий DCR: `redirect_uri`, scopes, брендинг)
  и `POST /api/ecosystem/gateway-keys`; валидация punycode/https/scopes/брендинга; kill-switch
  `ECOSYSTEM_PROVISIONING_DISABLED`; fail-closed при незаданном `ECOSYSTEM_KEY`; ответ регистрации
  сам ссылается на смоук из 4 curl. Скрипты переведены на то же ядро. +71 тест (всего 1941).
- 🔒 **Граница, найденная при проектировании:** экосистемный ключ один на всех, поэтому «обновить
  существующую запись» по HTTP = возможность перевесить чужого клиента на свой `redirect_uri`.
  Правило: создать новое — можно, тронуть существующее — только предъявив его текущий секрет
  (409/403); отключённую оператором запись self-serve **не воскрешает**.
- ✅ **ЗАДЕПЛОЕНО И ПРОВЕРЕНО 2026-07-29** (прод `68fedcf`, health 200). `ECOSYSTEM_KEY` и
  `RADAR_INVITE_CODE` заданы в `/etc/setka/setka.env` (бэкап `setka.env.bak-2026-07-29-0044`,
  значения — в root-only `/root/ecosystem-keys-2026-07-29-0044.txt`). Смоук на проде: без ключа
  `401`, чужой ключ `401`, кириллический `redirect_uri` → отказ с подсказкой про punycode, попытка
  перерегистрировать `sabantuy` на чужой адрес возврата → `409`, ключ шлюза для уже выданной
  KAZANSKAYA без секрета → `409`.
- ✅ **Круг ЕСА пройден целиком без человека** (клиент `portal`, 2026-07-29): саморег смоук-аккаунта
  → логин → `/oidc/authorize` → код → `/oidc/token` (access + id + refresh, scope `openid profile`)
  → `/oidc/userinfo` (`sub`, `name`). Аккаунт `smoke_esa` (роль `radar`), пароль в
  `/root/esa-smoke-account.txt`. **Грабля проверки:** кука ставится на `.вмалмыже.рф`, поэтому
  прогон с `127.0.0.1` бесполезен — `authorize` уводит на `/login`; гонять по публичному issuer'у.
