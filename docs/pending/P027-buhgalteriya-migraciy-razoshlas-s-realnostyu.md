Найдено 2026-08-09 при накате 078: `scripts/migrate.py status` показывает **31 pending**, среди них
070–077, которые на проде **фактически применены** (их таблицы и колонки работают: хэши ключей
шлюза, расширенные поля ad-клиентов, нормализация тем классификатора). Значит миграции накатывались
руками мимо раннера, а `applied_migrations` не пополнялась.

**Чем это опасно.** Раннер умеет только «применить всё pending» — выборочного режима нет. Тот, кто
однажды выполнит `migrate.py up` не глядя (а это документированная штатная команда после `git pull`),
прогонит по живой БД 31 файл разом. Большинство идемпотентны (`IF NOT EXISTS`), но не все:
**075 `gateway_keys_drop_plaintext.sql` содержит `DROP COLUMN`**. Повторный прогон DDL по таблице,
где уже живут ключи шлюза, — не та операция, которую хочется получить побочным эффектом рутинной
команды.

**Как накатывали 078 (обходной путь, повторяемый):** миграция применена напрямую тем же способом,
каким это делает раннер, и строка бухгалтерии дописана вручную —

```
ssh sarafan "sudo -u postgres psql -d setka -v ON_ERROR_STOP=1 -f ~/SETKA/database/migrations/<файл>.sql"
ssh sarafan "sudo -u postgres psql -d setka -c \"INSERT INTO applied_migrations (filename, sha256) VALUES ('<файл>.sql','<sha из status>') ON CONFLICT (filename) DO UPDATE SET sha256=EXCLUDED.sha256, applied_at=CURRENT_TIMESTAMP;\""
```

**Что сделать (не в этой сессии, нужен владелец).** Сверить каждую из 31 строки с фактическим
состоянием схемы и либо дописать в `applied_migrations` как применённую, либо применить. Это ровно
тот случай, где нельзя «прогнать и посмотреть»: сверка read-only, а решение по каждой — под
человеческим гейтом #025. Отдельный вопрос — дать раннеру режим «отметить применённой без
выполнения» (`mark-applied`), иначе расхождение накопится снова.
