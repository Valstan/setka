# Self-serve подключение к экосистеме (для проекта-клиента)

> Реализация [ADR-0010](../../../brain_matrica/adr/0010-ecosystem-direct-exchange.md) —
> решение владельца от 2026-07-28: внутри экосистемы стандартные подключения
> делаются **без человека в цикле**. Ни письма через Мозг, ни ручной процедуры
> на нашей стороне.

Оба канала SETKA выдаются **одной процедурой и одним ключом**:

| Что нужно | Эндпоинт | Что получите |
|---|---|---|
| Вход через ЕСА (единый вход экосистемы) | `POST /api/ecosystem/oidc-clients` | `client_id` + `client_secret` |
| Доступ к VK через наш шлюз | `POST /api/ecosystem/gateway-keys` | API-ключ для `X-API-Key` |

Аутентификация — заголовок `X-Ecosystem-Key`. Ключ лежит в вашей vault-комнате
КАРМАНа (выдаётся grant'ом проекту); значение через Мозг не ходит.

## 0. Если `ECOSYSTEM_KEY` у вас ещё нет — штатный маршрут выдачи

> Записано как штатная процедура по мандату brain 2026-08-23 §1б, после того как
> седьмой потребитель (РМЗ) упёрся в неё седьмым письмом. Восьмому письма писать
> не нужно — маршрут ниже.

**Всё, что описано в этом документе, начинается с ключа, которого у нового
потребителя нет.** Это [#116](../../../brain_matrica/cross-project-ideas/ideas/116-self-serve-needing-a-key-from-someone-elses-box.md)
в чистом виде: дверь самообслуживания заперта ключом, за которым надо идти тем же
путём, что и за содержимым. Скрывать это не надо — надо назвать процедуру.

**Маршрут — комната КАРМАНа, не GitHub Secret и не письмо.** Репозитории проектов
публичные; письма лежат в git. Секрет ходит только через vault.

1. **Проект заявляет потребность** — письмом через Мозг или строкой в реестре
   услуг: какой проект, какой контур (ЕСА / VK-шлюз), зачем.
2. **SETKA выпускает** (`scripts/issue_gateway_key.py` для шлюза,
   `scripts/register_oidc_client.py` для ЕСА — оба на боксе, под env приложения,
   вывод в root-only файл, **не в чат**) и **кладёт значение в свою комнату
   КАРМАНа** под тем именем, под которым потребитель положит его себе в env
   (`GATEWAY_KEY_<PROJECT>`, `ECOSYSTEM_KEY`, `ESA_CLIENT_SECRET_<CLIENT>`).
3. **Владелец выдаёт grant** `setka → <проект>` на это имя в GUI КАРМАНа под 2FA.
4. **Потребитель тянет по имени** своим vault-клиентом. Дальше он самообслуживается
   этим документом.

**Почему не «положить сразу в комнату потребителя».** Технически невозможно, и это
by design: в `POST /api/secrets` **нет адресата** — комната выводится из хеша
токена, а токен у каждого только свой. `provision` даёт `409` на живую комнату,
получатель grant'а не может **писать** выданное имя. Машинного пути в чужую комнату
не существует ни одного.

**Честная граница, которую надо закладывать в сроки.** Шаг 3 — **ручной ход
владельца**, и он противоречит обещанию [ADR-0010](../../../brain_matrica/adr/0010-ecosystem-direct-exchange.md)
«без человека в цикле». Обещание держится начиная со **второго** обращения проекта;
первое — операция с человеком в середине, потому что машинного grant-API у КАРМАНа
нет. Пока он не появится, «выдадим ключ» означает «выпустим сегодня, доставим —
когда владелец подойдёт к GUI», и планировать надо от этого, а не от `curl`.

## 1. Клиент ЕСА за один curl

```bash
ESA=https://xn--b1ae3a1a.xn--80adkdyec4j.xn--p1ai

curl -s -X POST "$ESA/api/ecosystem/oidc-clients" \
  -H "X-Ecosystem-Key: $ECOSYSTEM_KEY" \
  -H 'Content-Type: application/json' \
  -d '{
        "client_id": "example",
        "name": "Пример сервиса",
        "redirect_uris": ["https://xn--80aac7atuli.xn--p1ai/api/auth/callback"],
        "scopes": "openid profile email",
        "branding": {"title":"Пример сервиса","icon":"🔧","accent":"#0d6efd",
                     "sub":"Короткая подпись под заголовком"}
      }'
```

> Пример намеренно вымышленный. Раньше здесь стоял живой клиент `portal` со своими
> тогдашними значениями — к августу они разошлись с реальностью (сменился
> `redirect_uri`, добавился `email`), и документ продолжал учить неверному, ничем
> этого не показывая. **Работающий пример, скопированный с живой записи, стареет
> вместе с ней и молча.**

Ответ содержит `client_secret` — **он показывается ровно один раз** (в БД лежит
только scrypt-hash). Потеряли — не восстановить, только перевыпустить.

Что проверяется на входе (и почему):

- **`redirect_uris` — точные, `https`, ASCII.** Для доменов `.рф` обязателен
  punycode: OAuth сравнивает `redirect_uri` символ-в-символ, и кириллический
  вариант отвалится уже в бою ([G108]). `http` допустим только на `localhost` —
  для отладки.
- **`scopes`** — подмножество `openid profile email`, обязательно с `openid`.
  Это потолок: сверх него клиент claims не получит (152-ФЗ, минимизация).
- **`branding`** — карточка вашего сервиса на странице входа: `title`, `icon`,
  `accent` (`#rrggbb`), `sub`. Не передадите — на `/login` будет голое `name`.

## 2. Ключ VK-шлюза за один curl

```bash
curl -s -X POST "$ESA/api/ecosystem/gateway-keys" \
  -H "X-Ecosystem-Key: $ECOSYSTEM_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"project":"KAZANSKAYA","note":"импорт сообществ района"}'
```

Ключ возвращается один раз, дальше — в заголовке `X-API-Key` к
`POST /api/gateway/call`. Квоты висят **на ключе**
(`GATEWAY_QUOTA_PER_MIN` / `_PER_DAY` + общий бюджет шлюза), поэтому
самообслуживание не расширяет расход VK-токенов: лимит принадлежит ключу, а не
процедуре его получения.

## 3. Проверьте круг сами

Смоук ЕСА проходится четырьмя `curl`, без браузера и без VK-аккаунта —
[`esa-smoke-without-browser.md`](esa-smoke-without-browser.md). Тестовый
аккаунт заводится там же самореги: `POST /api/auth/register` с инвайт-кодом.

## Повторная заявка и ротация

Процедура идемпотентна, но **чужое тронуть нельзя**:

| Ситуация | Что будет |
|---|---|
| Новый `client_id` / проект | `201`-семантика: создаём, отдаём секрет |
| Своя запись + `current_secret` | обновляем поля; с `rotate_secret`/`rotate` — новый секрет |
| Существующая запись без секрета | `409 client_exists` / `key_exists` |
| Секрет не подошёл | `403` |
| Запись отключена оператором | `403 *_disabled` — включает только оператор |

Причина ограничения: экосистемный ключ **один на всех**, и без предъявления
секрета записи «обновить существующее» означало бы «перевесить чужой вход на
свой адрес возврата». Создание нового — безопасно, правка чужого — нет.

## Если что-то пошло не так

- `503 not configured` — на проде не задан `ECOSYSTEM_KEY` (наша сторона).
- `503 disabled` — выдача погашена kill-switch'ом
  `ECOSYSTEM_PROVISIONING_DISABLED=1` (реакция на утечку ключа; уже выданные
  клиенты и ключи при этом продолжают работать).
- `401` — ключ не тот. Проверьте, что берёте из vault-комнаты своего проекта.

Операторская сторона (аварийная выдача, отключение чужого ключа, импорт
env-ключей) — `scripts/register_oidc_client.py` и `scripts/issue_gateway_key.py`
на хосте. Ядро у HTTP и CLI **общее** (`modules/ecosystem/provisioning.py`),
разъехаться правилами им нечем.
