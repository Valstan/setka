# Карта доменов бокса SETKA — что где раздаётся и чего нельзя ломать

> Заказ владельца 2026-08-02: «у нас на сарафане много чего нацеплено и раздаётся на разные
> поддомены, это надо не забыть и иметь в виду, чтобы не сломать случайно новыми разработками».
> Этот файл — тот самый список. Правишь хосты, гейт авторизации или nginx — сверься сначала сюда.

Один процесс `uvicorn main:app` на `127.0.0.1:8000` обслуживает **четыре разных продукта** на
четырёх доменах. Приложение различает их по заголовку `Host`, nginx — по `server_name`.
Пятый домен на том же боксе (визитка) приложения не касается вовсе.

Плюс [`config/nginx_setka_http_default.conf`](../../config/nginx_setka_http_default.conf) —
`default_server` на 80-м порту для запросов с неизвестным `Host` (прямой заход по IP, внутренние
проверки). Его намеренно не трогаем: через него ходят локальные health-проверки, а апгрейд на https
сломал бы их без пользы — снаружи по IP публичный сертификат всё равно не предъявишь.

**Все конфиги бокса лежат в `config/nginx_*.conf` и ставятся оттуда.** Снято с прода и сверено
2026-08-02: до этого в git лежала версия `setka.conf` годичной давности (`listen 80`, TLS
закомментирован) — скопировавший её на бокс снял бы HTTPS с технического домена.

## Правила, из-за нарушения которых уже ломались

### 1. Одно решение — один владелец. Дублировать маршрут в nginx нельзя

**Инцидент 2026-08-02.** `радар.вмалмыже.рф` **зациклился для всех, кто вошёл**. Блок nginx создан
18.07, когда Радар жил на `/radar`, и содержал `location = / { return 302 /radar; }`. 26.07
интерфейс переехал на корень, приложение стало отвечать на `/radar` редиректом на `/` —
и две копии одного решения погнали пользователя по кругу: `/` → `/radar` → `/` → …

Аноним петли **не видел**: на первом же шаге его уводило на страницу входа. Поэтому баг прожил
неделю незамеченным и бил ровно по тем, кто уже вошёл, — по всем настоящим пользователям Радара.

**Правило:** маршрутизация внутри приложения (какой путь что показывает, куда редиректить) живёт
**только в приложении** (`is_radar_host`, `radar_canonical_redirect` в
[`modules/radar_id/vk_upstream.py`](../../modules/radar_id/vk_upstream.py), роуты в `main.py`).
nginx занимается транспортом: TLS, заголовки, лимиты тела, статика. Ловушка коварна тем, что оба
конфига по отдельности выглядят правильными.

**Как проверять:** цепочку редиректов гонять **через nginx (порт 80)** с живой сессией, а не мимо
него на `127.0.0.1:8000`. Мимо nginx петля не воспроизводится вовсе.

### 2. Схему запроса знает только заголовок от edge, не `$scheme`

TLS `.рф`-поддоменов терминируется на **edge-прокси Джино** (привязка и Let's Encrypt — в панели
провайдера, см. память `jino-subdomain-tls-via-panel`). До бокса запрос всегда приходит по http на
порт 80, поэтому `$scheme` в этих блоках **всегда «http»** и ничего не различает.

Правду знает `X-Forwarded-Proto` от edge (замер 2026-08-02: https-визит → `https`, http-визит →
`http`). Отсюда две переменные в [`config/nginx_maps.conf`](../../config/nginx_maps.conf):
`$setka_forwarded_proto` (передаём приложению) и `$setka_needs_https` (условие редиректа).
**Любой новый блок обязан использовать их, а не `$scheme`.**

Почему это не косметика: сессионная кука выдаётся с флагом `Secure`
([`web/api/auth.py`](../../web/api/auth.py)) — по голому http она не отправляется, и вход
не просто небезопасен, он **молча не работает**.

### 3. Редирект на https — только для GET/HEAD и только при явном `http`

Оба ограничения — про режим отказа, оба описаны в `nginx_maps.conf`:

- **явное `= "http"`**, а не «`!= https`»: если edge однажды перестанет слать заголовок, второй
  вариант даёт вечный редирект https→https и кладёт домен целиком, а чинится это только по SSH;
- **только GET/HEAD**: server-to-server POST (OIDC `token`, ingest рутины, ВК-шлюз) 301 бы сломал —
  клиенты на редиректе часто превращают POST в GET и теряют тело.

### 4. Голый http прятал целый класс поломок — после включения https они всплывают

Service Worker и Push API живут **только в secure context**: на голом http браузер молча отклоняет
регистрацию, и `.catch(() => {})` в шаблоне это проглатывал. Пока домены жили на http, любой дефект
PWA был невидим — а с https они включились разом. Найдено и починено 2026-08-02 тем же заходом:

- `/sw.js` отдавал **403** роли `radar` (путь не был публичным, а поблажка для радар-хоста написана
  на точное `/`). Следствие было неочевидным: `initPush()` показывал кнопку-колокольчик и вис
  навсегда на `navigator.serviceWorker.ready` — промис без регистрации не резолвится и не
  отклоняется, поэтому `.catch` не срабатывал;
- `sw.js` кэшировал жёсткий `'/radar'`, хотя на своём домене кабинет живёт на корне. Cache API
  отказывается класть redirected-ответ → `install` падал целиком;
- кука состояния ВК-входа ставилась **host-only**, а callback всегда приземляется на issuer —
  первая попытка входа после каждого выхода честно падала в «Сессия ВК-входа истекла».

**Правило:** правишь что-то, что раньше «не работало и так», — проверь, не было ли оно просто
спрятано. И держи `/sw.js`, манифест и прочие корневые пути радар-хоста в публичном списке: там
пускается только **точное** `/`, поэтому любой новый корневой путь по умолчанию даст 403 своим же.

### 5. Что публично на каком хосте — решает гейт, и он хост-зависимый

[`middleware/auth_gate.py`](../../middleware/auth_gate.py):

- `PUBLIC_EXACT` — публичный лендинг и его данные, **точным** совпадением пути (префикс открыл бы
  заодно любой будущий `/regions/links-*`);
- `PUBLIC_PREFIXES` — остальное публичное, включая машинные двери с собственной аутентификацией
  (`/api/gateway/`, `/api/classifier/`, `/api/ecosystem/`, `/oidc/token`, `/oidc/userinfo`,
  `/.well-known/`, `/auth/vk/`, `/api/health`). **Их нельзя затягивать в закрытый периметр** —
  умрут watchdog'и, шлюз, облачная рутина и OIDC-клиенты соседей;
- `SARAFAN_CLOSED_PUBLIC` — что публично везде, кроме домена сети (сейчас `/services`);
- `SARAFAN_ALLOWED_FOR_GUESTS` — выход из сессии и OIDC: не «содержимое сайта», иначе чужой юзер
  не смог бы даже разлогиниться с этого хоста;
- `_is_owner` — кто владелец: логин **при роли operator** либо `vk_user_id`. Логин-ветку сторожит
  роль потому, что логин выбирает регистрирующийся, а уникальность логина в Postgres
  регистрозависима (подробности — в `PENDING_FOLLOWUPS.md`).

Поведение всех хостов закреплено тестами в
[`tests/test_radar/test_auth_gate.py`](../../tests/test_radar/test_auth_gate.py) — если правка
хостов их роняет, сначала перечитай этот файл, а не правь тест.

### 6. У операторских страниц один дом — и адрес обязан ему соответствовать

`_operator_canonical_redirect` в [`middleware/auth_gate.py`](../../middleware/auth_gate.py):
браузерный GET операторской страницы на любом хосте, кроме `сарафан.вмалмыже.рф`, уводится
302-редиректом на канонический адрес с сохранением пути и query.

Зачем — две причины, и вторая дороже первой:

1. **Адрес врал о содержимом.** До 2026-08-18 приложение отдавало `/tokens`, `/ad`, `/posts` и
   дашборд на каждом из четырёх хостов. Владелец набирал `вход.вмалмыже.рф`, попадал в
   операторский САРАФАН, а строка браузера продолжала утверждать, что он на странице входа.
2. **На техническом домене вход зацикливался намертво.** Сессионная кука выдаётся на зону
   `.вмалмыже.рф` (`SESSION_COOKIE_DOMAIN`) и на чужой хост браузером не отправляется:
   `POST /api/auth/login` отвечал 200, следующий же запрос приезжал неаутентифицированным и снова
   падал на форму входа. Снаружи это выглядит как «не принимает пароль», хотя пароль верный.

Это тот же класс, что чинили 26.07 для Радара (`radar_canonical_redirect`) — тогда закрыли одну
зону из двух. **Заводя новый хост или новую зону, спрашивай: у её страниц есть канонический дом и
уезжают ли они туда?**

Границы механизма (ломать их — значит ломать соседей):

- **не трогает не-браузерные запросы** (`_wants_html`): на этих хостах сидят машинные интеграции,
  а часть клиентов ходит на ASCII-хост именно потому, что кириллический IDN им не по зубам;
- `OPERATOR_CANONICAL_EXEMPT` — что остаётся на месте: `/oidc/` (авторизация клиентов экосистемы
  обязана отрабатывать на issuer), `/radar` (своя зона со своим каноном), `/api/`, `/.well-known/`;
- публичные пути сюда не доходят вовсе — гейт отпускает их раньше;
- выключается вместе с многохостовой топологией: без `SESSION_COOKIE_DOMAIN` (локальная
  разработка) редиректа нет.

## Чек-лист перед правкой доменов, гейта или nginx

1. Прочитать этот файл и понять, **какие из четырёх продуктов** задевает правка.
2. Не дублировать в nginx решения приложения (правило 1).
3. Новый блок — с `$setka_forwarded_proto` и `$setka_needs_https` (правила 2–3).
4. Конфиг класть **в git** (`config/nginx_*.conf`) и ставить оттуда, а не править на боксе:
   на боксе конфиги переживают деплой, но не переживают переустановку и не видны на другой машине.
5. Проверять цепочку редиректов **через nginx с живой сессией**, отдельно анонимом и отдельно
   аутентифицированным — половина инцидентов видна только во втором случае.
6. `nginx -t` перед `reload`, бэкап заменяемого файла рядом. Reload с битым конфигом не страшен
   (nginx оставит старый), страшен **рабочий** конфиг с петлёй.
