# Грабля: не-ASCII текст в конфиг через `ssh "…"` из PowerShell теряется до записи в файл

Сегодня рекламодатели SETKA получили в личные сообщения вот это:

```
????????????, Михаил Кукушкин! ??????? ?? ???? ??????????? ??? ?????????? ?ПИЖАНКА - ИНФО? …
26 ?????????
https://???????.????????.??/regions/links
```

Три живых человека, полтора дня, полностью автоматическая рассылка. Делюсь, потому что грабля
не доменная: она ловит любой проект, где текст для людей живёт в конфиге на сервере, а конфиг
правится с Windows-машины.

## Что произошло

Текст авто-приветствия хранился в `AD_AUTO_GREETING_TEXT` в `/etc/setka/setka.env`. Накануне его
обновляли — командой вида `ssh host "… AD_AUTO_GREETING_TEXT='Здравствуйте, …' …"` из PowerShell.
Кодовая страница консоли не переварила кириллицу, и **каждая русская буква стала литеральным `?`
(байт `0x3F`) ещё до того, как строка дошла до сервера**. В файл легли уже вопросительные знаки.

Проверка — `od -c` по строке конфига: `0x3F` вместо UTF-8 пар `320 227 …`.

## Почему это не заметили полтора дня

Три обстоятельства, каждое из которых стоит проверить у себя:

1. **Порча избирательна и оттого выглядит как баг приложения.** Латиница, цифры, знаки препинания,
   URL-схема, плейсхолдеры `{author_name}` — всё уцелело. Разрушилась ровно кириллица. Сообщение
   осталось структурно правильным, поэтому первая гипотеза у всех (и у меня) была «код сломал
   кодировку при отправке», а не «в конфиге лежит мусор».
2. **Подставляемые из БД значения приходят нормальными.** Имя человека и название сообщества
   рендерились корректным UTF-8 посреди сплошных `?` — это дополнительно уводило от мысли, что
   испорчен сам шаблон. **Следствие для детектора: проверять надо шаблон, а не отрендеренный
   результат** — живые подстановки маскируют поломку.
3. **В петле нет человека.** Автоответ на то и автоответ: никто не читает, что ушло. Единственный
   свидетель — получатель, который просто молча уходит.

## Что сделали

- Значение восстановили из бэкапа конфига (последнего с целым UTF-8) — скриптом **на самом сервере**,
  так что байты ни разу не прошли через командную строку.
- Источник текста перенесли из env в БД: теперь он правится через веб-форму админки, то есть
  приезжает по HTTP как UTF-8. Ключ из env сняли — иначе он перебивал бы новый источник.
- В код добавили предохранитель: серия из трёх и более `?` подряд в шаблоне → рассылка не идёт,
  в лог ERROR. Порог в три знака выбран сознательно: «Что?? Уже?» — нормальный текст, а слово,
  схлопнутое в `?`, даёт 5–12 подряд.
- Пострадавшим переотправили корректный текст с короткой припиской-извинением.

## Что из этого переносимо

1. **Не-ASCII на сервер — только файлом или веб-формой, никогда аргументом команды.** `scp`, `ssh
   host 'cat > /path'` со stdin, форма в админке — всё это передаёт байты. Аргумент команды проходит
   через кодовую страницу консоли, и на Windows это лотерея. У нас уже была родственная заметка про
   inline-python в `ssh` из PowerShell — оказалось, тот же корень шире, чем казалось: страдает любой
   не-ASCII payload, не только код.
2. **Текст, который читают люди, не должен жить в env.** Env правится ровно тем способом, который эту
   грабля и создаёт, и не имеет ни истории правок, ни превью. БД + форма в админке дают и то и другое.
   Если в проекте есть переменная окружения с человеческим текстом — это кандидат на переезд.
3. **У каждой полностью автоматической исходящей ветки должен быть предохранитель на «мусор».** Там,
   где человек видит текст перед отправкой, проверка не нужна — он и есть проверка. Там, где не
   видит, дешёвый инвариант («в шаблоне не должно быть серии `?`», «длина в разумных пределах»,
   «плейсхолдеры раскрылись») стоит десяти строк и ловит класс отказов, который иначе обнаруживают
   клиенты.
4. **Бэкап конфига перед каждой правкой окупается не «когда всё упало», а вот в таких случаях.** У
   нас лежало полтора десятка датированных копий `setka.env`; именно в них нашёлся последний целый
   UTF-8, и восстановление заняло минуты вместо переписывания текста с нуля. Заметь: та часть текста,
   которая была дописана уже **после** последнего бэкапа, восстановлению не подлежала — из `?` слова
   не достаются. Частота бэкапов = сколько работы ты готов потерять.

Если это стоит гочи — оформи как считаешь нужным; проверять у соседей я не ходил, но подозреваю, что
конфиги с человеческим текстом есть не только у нас.
