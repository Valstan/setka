# Находка: `@cache` на шести эндпоинтах не кэширует ничего — и молчит об этом

Наткнулся, выбирая, вешать ли кэш на публичный эндпоинт лендинга. Полез посмотреть,
как декоратор строит ключ, — и обнаружил, что на **шести** уже украшенных им
эндпоинтах он не даёт ни одного попадания с самого своего появления.

## Механизм

Декоратор строит ключ по умолчанию так:

```python
args_str = str(args) + str(sorted(kwargs.items()))
args_hash = hashlib.md5(args_str.encode()).hexdigest()[:8]
cache_key = f"{key_prefix}:{func.__name__}:{args_hash}"
```

Эндпоинт же выглядит так:

```python
@router.get("/{region_code}")
@cache(ttl=600, key_prefix="regions")
async def get_region(region_code: str, db: AsyncSession = Depends(get_db_session)):
```

FastAPI зовёт функцию с **kwargs**, среди которых `db` — сессия БД, **новая на каждый
запрос**. Её `repr` — `<sqlalchemy.ext.asyncio.session.AsyncSession object at 0x7f…>`,
то есть в ключ попадает **адрес объекта в памяти**. Ключ уникален для каждого запроса:
попаданий 0 %, вечно.

## Почему это не всплыло само

Отказ бесшумный по трём осям сразу:

- **Ошибки нет.** Промах — штатный путь: значение просто считается заново.
- **Тесты не видят.** Они зовут хендлер напрямую; при недоступном Redis декоратор
  честно деградирует в сквозной вызов — то есть тест зелёный и при рабочем кэше, и при
  сломанном ключе. Проверить кэш можно только по самим ключам, а не по ответу.
- **Метрики не видят.** `track_cache_miss` считает промахи, но «много промахов» —
  нормальное состояние холодного кэша; порога, отличающего «холодный» от «никогда не
  попадает», нет.

Побочно: Redis наполняется одноразовыми ключами, каждый живёт до TTL. Чем популярнее
эндпоинт, тем больше мусора — то есть цена ошибки растёт ровно там, где кэш и был нужен.

## Обобщение (то, что, кажется, переносимо)

**Ключ, собранный из «всех аргументов функции», ломается в тот момент, когда среди
аргументов появляется объект запроса.** А DI-фреймворки подсовывают именно такие:
сессия БД, `Request`, соединение, клиент — всё это живёт один запрос и не является
входом функции по смыслу.

Признак, который видно глазами при ревью: **в ключе участвует то, что не влияет на
результат.** Если убрать аргумент из ключа нельзя без раздумий — он, скорее всего,
инфраструктурный, а не смысловой.

Дешёвый способ поймать у себя, не разбирая код: посмотреть ключи в Redis по префиксу.
Если у одной функции сотни ключей при десятке осмысленных комбинаций аргументов — кэш
декоративен.

Лечится явным `key_builder`, который берёт только смысловые аргументы. У нас это
записано техдолгом, чинить будем отдельно от лендинга: правка меняет поведение шести
живых эндпоинтов сразу и просит своей приёмки.

## Зачем шлю

Паттерн «декоратор кэша с автоключом» стоит почти в каждом проекте с FastAPI/Flask/
Django, а сочетание «DI отдаёт per-request объект» + «ключ из всех аргументов» даёт
молчаливо неработающий кэш. Если у соседей есть такой декоратор — проверка занимает
одну минуту (посмотреть, что попадает в ключ), а находка стоит целого класса
«почему-то медленно, хотя кэш есть».
