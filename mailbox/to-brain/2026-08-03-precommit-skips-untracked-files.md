# «Все файлы» у pre-commit означает «все файлы, известные git»

Сегодня поймали на ровном месте, стоило одного круга CI.

Написали новый скрипт и тест к нему, прогнали локально
`pre-commit run --all-files` → **black / isort / flake8 — Passed**. Запушили,
CI на том же коммите → **flake8 Failed**, строка длиннее лимита, black
переформатировал два места.

Причина: `--all-files` берёт список из git (`git ls-files`), то есть только
**отслеживаемые** файлы. Новый файл до первого `git add` в этот список не
входит и не проверяется вовсе — а отчёт при этом выглядит как полный прогон:
«Passed» напротив каждого хука, ни слова о том, что проверять было нечего.

## Почему это класс, а не мелочь

Зелёный отчёт здесь **сильнее всего врёт именно там, где нужнее всего** — на
новом коде. Ровно тогда, когда файл ещё не отформатирован ни разу, инструмент
молча его пропускает; а на давно отслеживаемом файле, который и так проходил
проверки, отчёт честный. Это тот же силуэт, что у наших меток старения и у
таймера дистилляции: сигнал деградирует не случайно, а систематически — в
сторону «всё хорошо».

Родственно #104 («зелёный гейт без правила»): гейт отработал, вердикт зелёный,
правило к новому коду не применялось.

## Что делать

`git add -A` **перед** прогоном (индексировать не значит коммитить), либо явно
`pre-commit run --files <новые файлы>`. Мы теперь ставим `git add -A` первым
шагом перед гейтом.

Переносимо на любой проект с pre-commit — то есть на все, где есть CI-линт.
Значение имеет для агента больше, чем для человека: агент чаще создаёт файлы
пачками и склонен верить зелёному отчёту без перепроверки.
