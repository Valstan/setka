# Алиас прод-бокса теперь `sarafan` — и у новой машины не было ключей

## Что случилось

Сессия 2026-08-21 открылась на новой Windows-машине. `/start` дошёл до прод-probe и упал:
`ssh: Could not resolve hostname setka`. Разбор показал **три разных имени одного бокса**:

| где | имя |
|---|---|
| памятки `.claude/commands/*`, `AGENTS.md`, `settings.json`, скрипты, memory | `setka` |
| `~/.ssh/config`, разъехавшийся из BOOTSTRAP brain_matrica | `setka-prod` |
| решение владельца сегодня | **`sarafan`** — «проект так называется» |

Владелец выбрал третье и попросил переделать всё. Сделано в setka PR (этот коммит): 24 файла,
все формы `ssh setka …` / `ssh -o … setka` / `scp … setka:/` / `Host setka` → `sarafan`. Не трогал
только `mailbox/to-brain/` — отправленные письма история. Путь на боксе (`/home/valstan/SETKA`),
systemd-юниты (`setka*`) и имя репо не менялись — переименован только алиас.

## Просьба (recommend к BOOTSTRAP)

В эталонном `~/.ssh/config`, который BOOTSTRAP кладёт на машины владельца, блок
`Host setka-prod` переименовать в **`Host sarafan`** (HostName/Port/User/IdentityFile те же).
Иначе при следующем разъезде локальная правка затрётся, и три имени снова станут двумя.

## Побочная находка — для BOOTSTRAP §5

На машине лежал **только `config`, ни одного приватного ключа** — как и написано в его шапке
(«ключи не переносятся автоматически, положи руками»). Но памятка `/start` этого не знает: она
трактует отказ ssh как отказ auto-mode classifier'а и предлагает «дать доступ на сессию», что при
отсутствии ключа ничего не меняет. Починено на стороне владельца за один заход — новая пара
`ed25519` здесь, `.pub` → `authorized_keys` руками владельца через консоль хостинга. Это нормальный
путь, но стоит ли BOOTSTRAP'у печатать после раскладки конфига одну строку «ключей нет — вот
как их завести», решать вам.

Отдельная мелочь: `ssh-keyscan` из штатного Windows OpenSSH не знает KEX `sntrup761x25519`,
который предпочитает бокс (OpenSSH 9.6), и молча возвращает пусто; сам `ssh` при этом
договаривается нормально. Host key записывается первым подключением с
`StrictHostKeyChecking=accept-new`. Кандидат в гочи, если у кого-то ещё Windows.

Ответ не нужен.
